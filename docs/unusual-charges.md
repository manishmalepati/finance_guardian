# Unusual-charge baseline and experiment

The Intelligence page ranks unusually large settled purchases for a selected date range. `GET /analytics/anomalies?start_date=YYYY-MM-DD&end_date=YYYY-MM-DD[&currency=USD][&account_id=UUID]` returns a score, the earlier median, reference count and kind, a plain-language reason, and canonical transaction IDs for drill-down. Scores rank deviations from earlier history; they are **not probabilities of fraud**. `PUT /analytics/anomalies/{transaction_id}/review` accepts `expected`, `unexpected`, or `unreviewed` with the same date range, currency, and optional account ID. The feedback table holds only transaction ID, decision, and timestamps.

The baseline uses up to three years of history before the selected start date. Every reference purchase must have a posted date strictly before the charge being scored, including when several purchases share a date. The first usable reference is five earlier purchases from the same merchant and account, then twelve in the same category and account, then twenty in the account. Currency never crosses a reference group. It compares the amount with the prior median and median absolute deviation (MAD), with a floor of 15% of the median or 2 currency units. A flag requires an excess of at least 10 units, a ratio of at least 1.8, and a robust score of at least 3.5. This first version flags unusually *high* amounts only. Account or category fallback can be less specific than merchant history.

The purchase population excludes pending, removed, superseded, credit/refund, transfer/card-payment, missing-currency, and nonpositive entries. Active categorization is reduced to one row per transaction before joining. Exact same-account/date/amount/currency/merchant statement/Plaid overlap is counted once, with surplus same-signature purchases retained. The additive `analytics.anomaly_reviews` migration leaves canonical ledger rows untouched. A verified encrypted local PostgreSQL backup preceded migration.

## Synthetic comparison, 2026-10-27

Run `python -m pip install -r evals/requirements-anomaly.txt` and `python -m evals.anomaly_benchmark`. The benchmark generates 180 normal training purchases, then 80 evaluation purchases with eight seeded high-amount events. It never reads the database. Both approaches score evaluation records using only earlier posted dates. Isolation Forest is fitted only on pre-evaluation records, with a fixed random seed. Its evaluation alert policy is top eight solely to compare equal alert budgets; the API does not load scikit-learn or serve its scores. [Isolation Forest's decision function is a ranking score](https://scikit-learn.org/stable/modules/generated/sklearn.ensemble.IsolationForest.html), not a calibrated fraud probability.

| Method | Precision at 8 | Seeded recall at 8 | Alerts per 100 evaluation purchases | Local runtime |
| --- | ---: | ---: | ---: | ---: |
| Robust amount baseline | 1.00 | 1.00 | 10.0 | 2.0 ms |
| Isolation Forest 1.9.1 | 0.75 | 0.75 | 10.0 | 167.8 ms |

The fixture tests only large amount spikes on ten regular synthetic merchants. The baseline's perfect synthetic result does not estimate precision on real spending; runtime depends on the machine. In the local real-data smoke check, 217 purchases were eligible and 18 charges were flagged over the selected 2026-08-01 to 2026-10-27 range. There are zero reviewed anomaly labels, so no real precision, recall, or false-positive rate can be reported. Keep Isolation Forest offline until enough user-reviewed `expected` and `unexpected` cases exist to compare both approaches on held-out time periods and inspect false positives. More synthetic scenarios, including frequency bursts and recurring price jumps, are needed before expanding the shipped detector.
