# Explain My Spending semantics

`GET /analytics/explain-spending` compares two chronological, nonoverlapping date ranges of at most 366 days each. Parameters: `prior_start`, `prior_end`, `current_start`, `current_end`, optional `account_id`, and a three-letter `currency` (default USD). The response includes exact decimal-string totals, category and merchant drivers, count and average-amount effects, transaction IDs, exclusions, period lengths, and a reconciliation difference.

The measure is **gross settled purchase debits**, not net expenses or cash flow. It includes only active, nonpending, nonremoved, nonsuperseded transactions in the selected currency and account scope. Known transfer and card-payment categories are excluded. Unclassified debits remain visible as uncertain spending. Credits, including possible refunds, are excluded until there is an explicit, verified expense link; this avoids silently calling a reimbursement income or attaching it to the wrong purchase. The UI states the policy.

An active categorization is selected by latest update and ID, so the query has one row per canonical transaction even if bad data creates two active category rows. The dbt staging join uses the same cardinality rule, and a dbt test detects the underlying data problem. Exact same-account/date/amount/direction/currency/merchant statement-Plaid pairs are paired by occurrence and the statement occurrence is removed from the comparison. Similar-looking pairs with different merchant text remain included and require reconciliation; no fuzzy match is silently trusted.

For each category or category-plus-merchant group, `delta = later total - earlier total`. For a group with purchases in both periods, the count effect is `(later count - earlier count) × earlier average`. The average-amount effect is the remaining cents of the group delta, so rounding never breaks reconciliation. New and vanished groups put the full delta in the count effect. Both positive and negative drivers are returned. Category and merchant sums must each equal the overall delta exactly or the request fails.

The API flags periods with different lengths. The UI defaults to the two most recent complete calendar months and allows four date selections. Drill-down uses existing transaction context and receipt views. No migration or database reset is required for this release.
